## 論点07 — 系譜を Model の自己参照で持つか、独立エンティティにするか

**ステータス: 決定済（2026-09-05）**

### 背景

`order.txt` §4 が明示的に投げている論点。`Training` が `source_model_id` と `output_model_id` を持つ以上、親子関係は `Training` から導出できるため、独立した系譜エンティティは素朴には冗長である。

### 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | `Model.parent_model_id` の自己参照のみ | 最小構成。実装が単純 | 学習以外の派生（インポート・形式変換・量子化）を表現できない。複数親（モデル統合）も不可 |
| B | `ModelDerivation` を独立エンティティにする | 派生の種別を持てる。将来の統合・変換にも耐える。祖先探索が軽い | エンティティが1つ増え、`Training` との整合を保つ責務が発生する |
| C | `Training` からの導出のみ | 冗長が一切ない | 非学習由来の派生を系譜に載せられない。祖先探索が毎回 `Training` 経由になる |

### 推奨

**案B。** `kind: transfer_learning | fine_tune | convert | quantize | import` を持たせる。

### 確認事項

- 「モデル形式の変換」「量子化版の生成」を将来行う可能性はあるか。あるなら案B以外は選べない。
- 複数モデルの統合（アンサンブル・マージ）を将来行う可能性はあるか。

### 影響範囲

`ModelDerivation` エンティティの有無、`Model.parent_model_id` 属性の有無、ER図。

### 決定

**案Bを採用**（2026-09-05）。`ModelDerivation` を独立エンティティとする。

- `kind` に `transfer_learning` / `fine_tune` / `convert` / `quantize` / `import` を持たせ、学習を伴わない派生も同じ系譜に載せる。
- 学習由来の派生は `training_id` で `Training` に紐づけ、系譜から学習履歴へ直接辿れるようにする。
- `Model.parent_model_id` は持たない（系譜の情報源を `ModelDerivation` に一本化する）。
- 多重度は将来のモデル統合に備えて N — N とする。

反映先: [01 方針7](./01-conceptual-er-model.md#方針7-系譜を-modelderivation-として独立させる論点07)

## 論点08 — Model Version を独立エンティティにするか

**ステータス: 決定済（2026-09-05）**

### 背景

`order.txt` §12 が挙げている論点。転移学習の出力は「同じモデルの新バージョン」ではなく「別のモデル」である。version 番号と lineage を同時に管理すると必ず矛盾する — 例えば Model B から2本派生したとき、両方が v2 になる。

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | `ModelVersion` を作らない。`Model` を不変ノードとし、系譜そのものをバージョン履歴として扱う |
| B | `ModelVersion` を独立エンティティとして持つ |
| C | 案A + `ModelFamily`（系列名・世代番号）を表示専用として追加する |

### 推奨

**案A。** 人間向けの世代表示が必要になった場合のみ案Cへ拡張する。その場合も `generation_no` は表示専用とし、識別子には使わない。

### 影響範囲

`ModelVersion` / `ModelFamily` エンティティの有無、モデル一覧UIの表示方法。

### 決定

**案Aを採用**（2026-09-05）。`ModelVersion` は作らない。`Model` を不変ノードとし、系譜そのものをバージョン履歴として扱う。

`ModelFamily` も現時点では導入しない。系列名・世代番号の表示が必要になった時点で案Cとして再検討する。その場合も `generation_no` は表示専用とし、識別子には使わない。

反映先: [01 方針8](./01-conceptual-er-model.md#方針8-modelversion-を持たない論点08)

## 論点09 — 推論結果をアノテーションの下書きとして再利用するか

**ステータス: 決定済（2026-09-05）**

### 背景

「モデルの推論結果を人が修正して学習データにする」（自動ラベリング）を想定するかどうかで設計が変わる。想定するなら `AnnotationSet` に `source` と由来の `InferenceTarget` を持たせる必要がある。

これがあると次の2つが可能になる。

- 「モデル出力 → 人が修正 → 次の学習データ → 次のモデル」という循環の追跡。
- 「モデルAの出力で学習したモデルB」というデータ汚染の検出。

### 推奨

機能としてスコープに含めるかは別途決めてよいが、**由来を記録する属性（`AnnotationSet.source`, `AnnotationSet.origin_target_id`）だけは最初から確保する。** 後から追加すると既存データの由来が永久に不明になる。

### 影響範囲

`AnnotationSet.source` / `origin_target_id`、`InferenceTarget` — `AnnotationSet` 間のリレーション。

### 決定

**属性のみ先に確保する**（2026-09-05）。自動ラベリング機能は初期スコープに含めないが、`AnnotationSet.source`（`manual` / `imported` / `from_detection`）と `origin_target_id`、および `InferenceTarget` — `AnnotationSet` のリレーションは最初から持つ。

反映先: [01 方針12](./01-conceptual-er-model.md#方針12-推論結果の由来を記録できるようにする論点09)

## 論点10 — 推論履歴をどこまで残すか（保持ポリシー）

**ステータス: 決定済（2026-09-05）**

### 背景

`order.txt` §11 の設計思想④に従い推論を全件保存すると、1回の実行で数十件の `Detection` が生まれ、レコードが際限なく増える。ブラウザストレージには容量上限があり、運用開始後すぐに問題になる。

### 選択肢

- 全件永久保存
- 直近N件 + ユーザーが `pinned` したものは永続
- 期間経過で自動削除

### 推奨

**`pinned` フラグ + 上限件数での自動削除。** ER 的には `Inference.pinned` の属性1つで足りる。

### 影響範囲

`Inference.pinned` 属性、削除ポリシーの実装。

### 決定

**pinned + 上限件数での自動削除を採用**（2026-09-05）。ユーザーが pinned した推論は永続、それ以外は上限件数を超えた分から古い順に自動削除する。上限件数の具体値は実装フェーズで決める。

反映先: [01 方針14](./01-conceptual-er-model.md#方針14-推論履歴は-pinned--上限件数で管理する論点10)

## 論点11 — 推論を1画像単位にするか、バッチ単位にするか

**ステータス: 決定済（2026-09-05）**

### 背景

`Inference` を「1実行 = 1画像」とすると単純だが、複数画像をまとめて処理するUIを作った時点で構造を変える必要が出る。

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | `Inference`（model + image）→ `Detection` の2階層 |
| B | `Inference`（実行）→ `InferenceTarget`（画像単位）→ `Detection` の3階層 |

### 推奨

**案B。** 1画像だけの場合も `InferenceTarget` が1件になるだけでコストはほぼない。画像ごとの成否（`status`）と処理時間（`elapsed_ms`）も自然に持てる。

### 確認事項

- 複数画像の一括推論をUI要件に含めるか。

### 影響範囲

`InferenceTarget` エンティティの有無、`Detection` の親、論点09のリレーション。

### 決定

**案Bを採用**（2026-09-05）。`Inference` / `InferenceTarget` / `Detection` の3階層とする。

`InferenceTarget` は `status`（`succeeded` / `failed` / `skipped`）と `elapsed_ms` を持ち、画像ごとの成否と処理時間を記録する。`Detection` の親は `InferenceTarget` となる。

なお「複数画像の一括推論をUI要件に含めるか」は本決定とは独立に判断してよい。構造として先に対応させておく。

反映先: [01 方針9](./01-conceptual-er-model.md#方針9-推論を3階層にする論点11)

## 論点12 — 前処理・実行パラメータをどちらに置くか

**ステータス: 決定済（2026-09-05）**

### 背景

パラメータには性質の異なる2種類がある。

- **モデル固有** — 入力サイズ、正規化、letterbox。変えると結果が壊れる。
- **実行ごとに変える** — 信頼度しきい値、NMS の IoU しきい値、最大検出数。

混在させると「なぜこの結果になったか」を再現できない。

### 推奨

前処理仕様は `Model.input_spec`、しきい値類は `Inference` の属性。

### 影響範囲

`Model.input_spec`、`Inference.conf_threshold` / `iou_threshold` / `max_detections`。

### 決定

**Model と Inference に分離する**（2026-09-05）。前処理仕様は `Model.input_spec`、しきい値類は `Inference` の属性とする。`Inference` 側への `input_spec` のスナップショットは行わない（`Model` が不変であるため、参照だけで再現できる）。

反映先: [01 方針15](./01-conceptual-er-model.md#方針15-前処理仕様とスレッショルドを分離する論点12)

## 論点13 — 失敗・中断した Training をどう扱うか

**ステータス: 決定済（2026-09-05）**

### 背景

ブラウザ上での学習は、タブを閉じる・メモリ不足・バックグラウンド化などで容易に中断する。長時間ジョブが中断される前提の設計が必要。

### 推奨

`Training.status`（`running` / `completed` / `failed` / `cancelled`）を持たせ、失敗した学習も記録として残す（設計思想③）。`output_model_id` は nullable とし、`Training : Model(output)` を 1 : 0..1 とする。

### 確認事項

- 中断からの再開（checkpoint 保存）を要件に含めるか。含める場合 `TrainingCheckpoint` エンティティが追加で必要になる。

### 影響範囲

`Training.status` / `output_model_id` の nullable 化、`TrainingCheckpoint` の要否。

### 決定

**status で記録し、再開はサポートしない**（2026-09-05）。`Training.status`（`running` / `completed` / `failed` / `cancelled`）を持ち、失敗・中断した学習も記録として残す。`output_model_id` は nullable。`TrainingCheckpoint` は導入せず、中断した学習はやり直しとする。

反映先: [01 方針13](./01-conceptual-er-model.md#方針13-失敗中断した-training-も記録として残す論点13)

## 論点14 — 開発者提供 Base Model の同一性と更新

**ステータス: 決定済（2026-09-05）**

### 背景

アプリ更新で Base Model が差し替わったとき、既にそれを親として派生したユーザーモデルの系譜が壊れないようにする必要がある。

### 推奨

Base Model は不変IDで配布し、更新版は「別のモデル」として追加する。既存の親子関係は書き換えない。

### 確認事項

- Base Model のメタ情報は初回起動時に全件登録するか、使用時に遅延登録するか。重みのダウンロード量に関わる。

### 影響範囲

`Model.origin = builtin` の扱い、初期データ投入の設計。

### 決定

**メタは全件登録、重みは遅延取得**（2026-09-05）。Base Model は不変IDで配布し、更新版は「別のモデル」として追加する。既存の親子関係は書き換えない。メタ情報（名前・クラス体系・入力仕様）は初回起動時に全件登録し、重みは実際に使用する時点でダウンロードする。

反映先: [01 方針18](./01-conceptual-er-model.md#方針18-base-model-はメタを全件登録し重みは遅延取得する論点14)

## 論点15 — 削除の扱い（参照整合性）

**ステータス: 決定済（2026-09-05）**

### 背景

学習に使った画像や、推論履歴が参照している画像をユーザーが削除できるとすると、過去の `Training` / `Inference` の追跡性が失われる。一方でブラウザの容量制約上「一切削除できない」も現実的ではない。

### 推奨

論理削除（`deleted_at`）を基本とし、参照されている実体（`ImageBlob` / `ModelArtifact`）のみ物理削除を許す。`Image` / `Model` のメタは残るため、系譜と履歴は保たれる。

この決定に伴い `ImageBlob` を `Image` から分離するかも確定する（[01 §3](./01-conceptual-er-model.md#a-画像アノテーション資産) で「暫定」としている箇所）。

### 確認事項

- 「画像を消したがアノテーションと `Detection` は残っている」状態をUIでどう見せるか。

### 影響範囲

`ImageBlob` エンティティの有無、`Image.deleted_at` などの論理削除属性、削除UIの仕様。

### 決定

**論理削除 + 実体のみ物理削除を採用**（2026-09-05）。`Image` / `Model` のメタは `deleted_at` による論理削除とし、物理削除は `ImageBlob` / `ModelArtifact` のみ許す。この決定により `ImageBlob` の分離が確定した。

削除UIの表現（「画像を削除したがアノテーションと `Detection` は残っている」状態の見せ方）は実装フェーズで詰める。

反映先: [01 方針16](./01-conceptual-er-model.md#方針16-削除は論理削除を基本とする論点15)

## 論点16 — Project / Workspace を導入するか

**ステータス: 決定済（2026-09-05）**

### 背景

導入すると一覧のスコープ分割、一括エクスポート、用途ごとのクラス体系分離が自然になる。導入しない場合は全エンティティがフラットに並ぶ。

後から全エンティティに `project_id` を足すのはマイグレーションコストが高いため、早期に決める必要がある。

### 確認事項

- 1ユーザーが同時に扱う用途は単一か複数か。複数なら最初から導入を推奨する。

### 影響範囲

`Project` エンティティの有無、ほぼ全エンティティの `project_id` 属性。

### 決定

**導入する**（2026-09-05）。`project_id` の付与範囲は以下とした。

| 区分 | エンティティ |
| --- | --- |
| `project_id` を持つ | `Image`, `LabelSet`, `Dataset`, `Model`, `Training`, `Evaluation`, `Inference` |
| 持たない（親から辿れる） | `AnnotationSet`, `AnnotationObject`, `DatasetVersion`, `DatasetItem`, `TrainingMetric`, `EvaluationMetric`, `InferenceTarget`, `Detection`, `ModelDerivation` |
| 持たない（横断共有） | `ImageBlob`, `ModelArtifact` |

`ImageBlob` / `ModelArtifact` を横断共有としたのは、`content_hash` / `checksum` による重複排除の対象であり、プロジェクトをまたいで同一実体が参照されうるため。

この決定から、Base Model の所属とプロジェクト間参照の可否という新たな判断が必要になった。論点18として起票する。

反映先: [01 方針10](./01-conceptual-er-model.md#方針10-project-を導入する論点16)

## 論点17 — ID採番とポータビリティ

**ステータス: 決定済（2026-09-05）**

### 背景

ブラウザ完結 = データは端末ローカルに閉じる。将来のサーバー同期・端末間移行・チーム共有を考えるなら、連番ではなく衝突しないIDが必要。

### 推奨

全エンティティで UUID / ULID を採番する。将来サーバーへ拡張する際にID再割当てが不要になる。

### 確認事項

- エクスポート単位は何か。モデル単体か、系譜ごとか、`Dataset` + `Model` 一式か。単位が決まると、エクスポートに必要なメタ情報も決まる。

### 影響範囲

全エンティティの主キー方式、エクスポート機能の仕様。

### 決定

**UUID / ULID 採番、エクスポート単位は Project 一式 + モデル単体**（2026-09-05）。`Project` を主なエクスポート単位とし、補助的にモデル単体の書き出しも可能とする。

論点18で `Project` を完全分離としたため、`Project` 一式のエクスポートで系譜が完結する。

反映先: [01 方針17](./01-conceptual-er-model.md#方針17-id-は-uuid--ulidエクスポート単位は-project論点17)

## 論点18 — Project のスコープ境界

**ステータス: 決定済（2026-09-05）**

### 背景

論点16で `Project` の導入を決定したことにより、次の判断が新たに必要になった。

1. **開発者提供 Base Model（`origin = builtin`）はどのプロジェクトに属するか。** プロジェクトごとに複製すると同じ重みが重複し、方針6（重みの容量削減）と衝突する。
2. **プロジェクト間で資産を参照できるか。** 例えばプロジェクトAの `Image` をプロジェクトBの `Dataset` に入れられるか、プロジェクトAで学習した `Model` をプロジェクトBで推論に使えるか。
3. **プロジェクトを削除したとき、横断共有される `ImageBlob` / `ModelArtifact` をどう扱うか。**

### 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | 完全分離。`project_id` は必須で、プロジェクト間参照を一切許さない。Base Model のみ `project_id = null` のグローバル資産とする | 境界が明確。エクスポートが単純 | 同じ画像を複数プロジェクトで使うたびに登録し直す必要がある |
| B | Base Model に加えユーザーモデルもプロジェクト間で参照可とする | モデルの再利用が容易 | 系譜がプロジェクトをまたぎ、エクスポート単位の判断が複雑になる |
| C | `project_id` を nullable とし、null をグローバル資産として全プロジェクトから参照可とする | 柔軟 | 「どこに属するか曖昧な資産」が増え、一覧・削除の仕様が複雑化する |

### 推奨

**案A。** ただし Base Model は `project_id = null` の例外として扱う。

理由: `order.txt` の中心的な要件はモデル系譜の追跡であり、系譜がプロジェクト境界をまたぐと「どこまでをエクスポートすれば系譜が完結するか」が定義できなくなる。プロジェクト間でモデルを使い回したい要求が実際に出てから案Bへ拡張する方が安全。

### 確認事項

- 同じ画像を複数プロジェクトで使う要求はあるか。ある場合、`ImageBlob` の共有だけで容量的には足りるか（`Image` メタの重複は許容できるか）。
- プロジェクト削除は論理削除か物理削除か。論点15と併せて決める。

### 影響範囲

`Model.project_id` の nullable 化、`Dataset` / `Inference` から他プロジェクトの資産を参照できるかの制約、エクスポート機能の単位（論点17と関連）。

### 決定

**案Aを採用**（2026-09-05）。`Project` は完全分離とし、プロジェクト間の資産参照を許さない。開発者提供 Base Model のみ `project_id = null` のグローバル資産として例外的に全プロジェクトから参照できる。

`Model.project_id` は nullable とするが、`origin = builtin` 以外で null を許さない。プロジェクト削除が論理削除か物理削除か、および参照されなくなった `ImageBlob` / `ModelArtifact` の回収方法は実装フェーズで詰める。

反映先: [01 方針11](./01-conceptual-er-model.md#方針11-プロジェクト間の参照を許さない論点18)

## 論点19 — 実行スレッド構成

**ステータス: 決定済（2026-09-05）**

### 背景

推論も転移学習もブラウザ内で実行する。学習は数分〜数十分かかりうるため、メインスレッドで回すとUIが完全に固まる。一方でモデルの重みは数十MB あり、スレッド間でコピーすると転送コストとメモリのピークが問題になる。

### 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | 学習のみ Worker、推論はメインスレッド | 構成が単純。推論の実装が楽 | 大きな画像の推論でUIが数百ms止まる |
| B | 学習用 Worker と推論用 Worker を分ける | 用途ごとに独立。学習中でも推論できる | 同じ重みを2つのWorkerが持ちうる。メモリのピークが上がる |
| C | 単一の ML Worker に学習と推論を集約 | 重みのロードを共有できる。メモリ効率が良い | 学習中は推論が待たされる（キュー制御が必要） |

### 推奨

**案C。** ML Runtime を1つの Worker に集約し、Application Layer からはジョブキュー経由で依頼する。

理由: ブラウザのメモリ上限が最大の制約であり、同じ重みを二重に持つ構成は避けたい。「学習中に推論もしたい」という要求は、学習が長時間かかること自体がUX上の問題であり、並行実行で解くべきではない。

### 影響範囲

`InferenceEngine` / `TrainingEngine` の実装配置、進捗通知の経路（論点21）、重みの受け渡し方式。

### 決定

**案Cを採用**（2026-09-05）。単一の ML Worker に学習と推論を集約し、Application Layer からはジョブキュー経由で依頼する。

あわせて**複数タブでの同時学習を許さない**ことを決定した。2つ目のタブでの学習開始はブロックする。排他の具体的な仕組み（Web Locks API など）は実装フェーズで選ぶ。この判断により、論点21の回収方式が案X（起動時の一括処理）で足りることになった。

反映先: [03 §4 実行スレッド構成](./03-system-architecture.md#実行スレッド構成論点19)

## 論点20 — ML Runtime の抽象化粒度

**ステータス: 決定済（2026-09-05）**

### 背景

`order.txt` §11 ⑥「アプリケーション層が特定のMLライブラリに直接依存しない構造」をどこまで徹底するか。抽象化を細かくするほど差し替えは楽になるが、ランタイム固有の最適化が使えなくなる。

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | 粗い抽象。`InferenceEngine.detect(model, image, params) → Detection[]` のように、ユースケース単位のインターフェースのみ定義する |
| B | 細かい抽象。テンソル操作・レイヤー・オプティマイザまで抽象化する |
| C | 中間。推論・学習のユースケース単位に加え、前処理と後処理（NMS など）を差し替え可能な単位として切り出す |

### 推奨

**案A。** ユースケース単位のインターフェースに留める。

理由: 案Bは事実上MLフレームワークを自作することになり、差し替えの容易さと引き換えに実装コストが跳ね上がる。ERモデルで決めた `Model.input_spec`（前処理仕様）と `Inference` のしきい値がインターフェースの引数として過不足なく揃っているため、粗い抽象でも情報は落ちない。

前処理・後処理の差し替えが必要になった時点で案Cへ拡張できる。

### 影響範囲

`InferenceEngine` / `TrainingEngine` / `ModelLoader` のインターフェース定義。

### 決定

**案Cを採用**（2026-09-05）。ユースケース単位のインターフェースに加え、`Preprocessor` と `Postprocessor` を差し替え可能な Port として切り出す。

推奨は案A（粗い抽象のみ）だったが、前処理（リサイズ・正規化・letterbox）と後処理（デコード・NMS）はモデル形式ごとに差が大きく、ここを固定するとランタイムを替えたときにユースケース側の実装まで書き換えることになる、という判断で案Cを採った。

`Preprocessor` は `Model.input_spec`（方針15）を入力とするため、モデルのメタ情報だけで挙動が決まり、ユースケース側は差し替えを意識しない。モデル形式ごとにどう実装を選択するか（`Model` に識別子を持たせるか、`ModelLoader` が判定するか）は実装フェーズで決める。

反映先: [03 §5 Port](./03-system-architecture.md#port抽象インターフェース)

## 論点21 — 学習の進捗通知と、中断した Training の回収

**ステータス: 決定済（2026-09-05）**

### 背景

方針13で「失敗・中断した Training も記録として残し、再開はサポートしない」と決めた。これを実際に成立させるには2つの仕組みが要る。

1. epoch ごとの進捗を Worker から受け取り、`TrainingMetric` として保存し、UIに反映する経路。
2. タブが閉じられて `status = running` のまま残った `Training` を、次回起動時に検出して `cancelled` に倒す処理。

2 は「異常終了したので `status` を書き換える」処理そのものが実行されないまま終わるため、次回起動時のクリーンアップでしか回収できない。

### 選択肢

進捗通知の方式:

| 案 | 内容 |
| --- | --- |
| A | Worker から postMessage で通知し、Application Layer が `TrainingMetric` を保存してUIに流す |
| B | Worker が直接ストレージに書き、UIはストレージの変更を購読する |

回収の方式:

| 案 | 内容 |
| --- | --- |
| X | 起動時に `status = running` の `Training` を全件 `cancelled` にする |
| Y | ハートビート（`last_heartbeat_at`）を持たせ、一定時間更新がないものだけ `cancelled` にする |

### 推奨

**A + X。** 進捗は postMessage で Application Layer に集約し、起動時に `running` のまま残った `Training` を一括で `cancelled` にする。

理由: 案Bは Worker がストレージ実装を知る必要があり、論点20の抽象化方針と衝突する。回収は、そもそも同時に複数タブで学習を走らせる想定がないため、ハートビートを持たずとも起動時の一括処理で足りる。複数タブ同時実行を許すなら案Yが必要になるため、そこは先に決めたい。

### 確認事項

- 複数タブで同時に学習を走らせることを許すか。許さないなら、2つ目のタブで学習開始をブロックする仕組みが必要。

### 影響範囲

`Training.status` の遷移責務、`TrainingMetric` の書き込み経路、起動時処理の追加、（案Yを採る場合）`Training` へのハートビート属性追加。

### 決定

**案A + 案Xを採用**（2026-09-05）。進捗は postMessage で Application Layer に集約し、`TrainingMetric` の保存とUIへの反映はそこで行う。中断した `Training` は、起動時に `StartupService` が `status = running` のものを一括で `cancelled` にする。

論点19で複数タブでの同時学習を許さないと決めたため、ハートビート（案Y）は不要。**ERモデルへの変更は発生しない。**

反映先: [03 §5 StartupService](./03-system-architecture.md#application-layer) / [03 §6.4](./03-system-architecture.md#64-起動時処理)

## 論点22 — Base Model の配信方式

**ステータス: 決定済（2026-09-05）**

### 背景

方針18で「メタは初回起動時に全件登録、重みは使用時に取得」と決めた。その取得元をどう構成するか。

### 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | アプリと同一オリジンの静的ファイルとして配信 | CORS 不要。構成が単純 | アプリのデプロイと Base Model の更新が連動してしまう |
| B | CDN / 別オリジンから配信 | モデルだけを差し替えられる。配信コストを分離できる | CORS 設定が必要。オフライン時の扱いが複雑になる |
| C | アプリにバンドルする | 完全オフラインで動く | 初回ロードが数十MB になり、使わないモデルも落とす |

### 推奨

**案A。** 同一オリジンの静的ファイルとし、メタ情報のカタログ（JSON）と重みを分けて配置する。

理由: 方針18で重みを遅延取得と決めたため案Cは選べない。案Bの利点はモデル更新の独立性だが、方針18により「更新版は別のモデルとして追加」するので、カタログJSONを差し替えれば同一オリジンでも同じことができる。

### 影響範囲

`BaseModelCatalog` の実装、デプロイ構成、論点24（オフライン動作）との関係。

### 決定

**案Aを採用**（2026-09-05）。アプリと同一オリジンの静的ファイルとして配信し、メタ情報のカタログ（JSON）と重みを分けて配置する。

方針14により「更新版は別のモデルとして追加」するため、モデルの追加・更新はカタログJSONの差し替えで対応でき、別オリジン（案B）にする必要がない。

反映先: [03 §3 全体構成](./03-system-architecture.md#3-全体構成)

## 論点23 — 容量超過（QuotaExceeded）時の扱い

**ステータス: 決定済（2026-09-05）**

### 背景

ブラウザストレージには容量上限があり、超過すると書き込みが例外で失敗する。本システムは画像・アノテーション・モデル重み・推論履歴をすべて保存するため、通常運用で上限に到達しうる。

方針6・14・16で「重みは破棄できる」「推論履歴は自動削除する」「実体のみ物理削除できる」と決めており、解放の手段は用意されている。問題は**いつ誰が実行するか**。

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | 事前監視。`StorageQuotaService` が定期的に使用量を確認し、閾値を超えたらユーザーに通知して破棄を促す |
| B | 事後対応。書き込み失敗を捕捉してから解放を試み、リトライする |
| C | A + B の併用 |

### 推奨

**案C。** 事前に警告を出しつつ、それでも失敗した場合はリトライする。

理由: 学習の完了時にモデル重みの書き込みが失敗すると、数十分の学習結果が失われる。事前監視だけでは取りこぼしがあり、事後対応だけでは失敗が突然起きる。

学習開始前に「必要な空き容量の見積もり」を出して警告する仕組みも検討したい。

### 影響範囲

`StorageQuotaService` の責務、各 Repository の書き込みエラー処理、UI の警告表示。

### 決定

**案Cを採用**（2026-09-05）。`StorageQuotaService` が使用量を監視して閾値超過で警告しつつ、書き込み失敗時には解放を試みてリトライする。

学習完了時の重み書き込みが失敗すると数十分の学習結果が失われるため、事前監視だけでは取りこぼしがあり、事後対応だけでは失敗が突然起きる。警告の閾値、および学習開始前の必要容量の見積もり方法は実装フェーズで決める。

反映先: [03 §5 StorageQuotaService](./03-system-architecture.md#application-layer)

## 論点24 — オフライン動作 / PWA 化の要否

**ステータス: 決定済（2026-09-05）**

### 背景

ユーザーデータはすべてブラウザ内にあるため、一度アプリと重みを取得すればオフラインでも動作しうる。Service Worker でアプリ本体をキャッシュすれば PWA として成立する。

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | 対応しない。常にオンライン前提 |
| B | アプリ本体のみキャッシュ。Base Model の重みは取得済みのものだけオフラインで使える |
| C | フル PWA。インストール可能にし、重みも積極的にキャッシュする |

### 推奨

**案B。** アプリ本体をキャッシュし、既に取得済みの重みで動作できる状態を目指す。

理由: 方針18で重みを遅延取得と決めたため、未取得のモデルはオフラインで使えないのが自然な帰結。それ以上のことをすると、案Cは「使うかわからないモデルを先読みする」ことになり方針18と矛盾する。

案Bは他の設計に影響を与えないため、実装フェーズで後から追加できる。

### 影響範囲

Service Worker の有無、デプロイ構成。他のコンポーネントには影響しない。

### 決定

**案Bを採用**（2026-09-05）。Service Worker でアプリ本体をキャッシュし、既に取得済みの重みで動作できる状態を目指す。未取得のモデルはオフラインで使えない。

他のコンポーネントに影響しないため、実装フェーズで後から追加できる。キャッシュ戦略とアプリ更新時の扱いは実装フェーズで決める。

反映先: [03 §7](./03-system-architecture.md#7-決定した論点)

## 論点25 — 実体（画像・重み）の格納先

**ステータス: 決定済（2026-09-05）**

### 背景

保存するデータには性質の異なる2種類がある（[04 §2.3](./04-storage-design.md#23-保存するデータの性質が2種類ある)）。メタデータは件数が多く検索が要るが1件は小さい。実体は件数が少ないが1件が数百KB〜数十MB ある。

IndexedDB はインデックスとトランザクションを持つがバイナリの大容量は苦手、OPFS は大容量に強いが検索できない。

### 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | メタは IndexedDB、実体は OPFS | それぞれの得意分野に合う。部分読み出し・ストリーミングが使える | 2つのストレージにまたがるため書き込みが原子的にならない（論点27） |
| B | すべて IndexedDB | トランザクションが1つにまとまり整合性の管理が単純 | 数十MBの値の読み書きが重い。ブラウザによっては上限に当たりやすい |
| C | メタは IndexedDB、実体は Cache Storage | fetch との相性が良く Base Model のキャッシュと統一できる | 本来HTTPレスポンスのキャッシュ用途。生成物の保管には意味論が合わない |

### 推奨

**案A。** ただし OPFS のブラウザ対応状況は実装フェーズで確認し、利用できない環境では `BlobStore` の IndexedDB 実装にフォールバックする。`BlobStore` を Port として切ってあるため（[03 §5](./03-system-architecture.md#port抽象インターフェース)）、この差し替えは他の層に影響しない。

### 影響範囲

`BlobStore` の実装、トランザクション設計（論点27）、孤児ファイルのGC処理。

### 決定

**案Aを採用**（2026-09-05）。メタデータは IndexedDB、実体は OPFS に置く。OPFS が利用できない環境では `BlobStore` の IndexedDB 実装にフォールバックする。

`BlobStore` を Port として切ってあるため（[03 §5](./03-system-architecture.md#port抽象インターフェース)）、フォールバックは他の層に影響しない。OPFS のブラウザ対応状況の確認と、フォールバック実装を実際に用意するかの判断は実装フェーズで行う。

反映先: [04 §3.2](./04-storage-design.md#32-方針)

## 論点26 — 永続化要求（`persist()`）の扱い

**ステータス: 決定済（2026-09-05）**

### 背景

ブラウザは、ディスク容量が逼迫したときにオリジンのデータをまとめて破棄することがある。既定の保存モードは best-effort であり、消去の対象になる。

**これは `order.txt` §11 の設計思想③「データを捨てない」と真っ向から衝突する。** 数十分かけて学習したモデルも、収集したアノテーションも、アプリの実装とは無関係に失われうる。

`navigator.storage.persist()` で永続化を要求でき、許可されると自動削除の対象から外れる。ただし許可条件はブラウザごとに異なり、拒否されることもある。問題は**拒否された状態でアプリがどう振る舞うか**。

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | 起動時に `persist()` を要求し、拒否されたら警告バナーを常時表示して、エクスポート（方針17）を促す |
| B | 学習やアノテーション作成など、失うと痛い操作の直前に要求する |
| C | 要求するが、拒否されても何もしない |

### 推奨

**案A + B の併用。** 起動時に一度要求し、拒否された状態で学習を開始しようとしたときに再度警告する。

理由: 拒否されたまま黙って使わせるのは、設計思想③に対して不誠実。一方でブラウザによっては「サイトを訪問し続ける」「ブックマークされる」などの条件で後から許可されるため、一度の拒否で諦めるべきでもない。

エクスポート機能（方針17）は、この状況における唯一の保険として位置づけられる。

### 確認事項

- 永続化が拒否された環境で、学習など長時間の操作を**ブロックする**か、警告に留めるか。

### 影響範囲

`StartupService` の起動時処理、UIの警告表示、エクスポート機能の優先度。

### 決定

**要求 + 警告、操作はブロックしない**（2026-09-05）。起動時に `persist()` を要求し、拒否された場合は警告バナーを常時表示してエクスポートを促す。学習開始時にも再度警告するが、**操作自体は許可する。**

拒否された環境で学習をブロックする案は採らない。ブラウザ側の判断次第で主機能が使えなくなるため。代わりにエクスポート機能（方針17）を「永続化が得られない環境における唯一の保険」と位置づけ、実装の優先度を上げる。

反映先: [04 §2.1](./04-storage-design.md#21-データを捨てないを脅かす最大のリスク)

## 論点27 — IndexedDB / OPFS 間の不整合の回復方式

**ステータス: 決定済（2026-09-05）**

### 背景

論点25で案Aを採る場合、IndexedDB のトランザクションが OPFS への書き込みを含められないため、学習完了時の4件（`ModelArtifact` / `Model` / `ModelDerivation` / `Training`）の書き込みが原子的にならない。

起こりうる不整合は2つ。

| 状態 | 影響 |
| --- | --- |
| OPFS に重みがあるが IndexedDB にメタがない | 孤児ファイル。容量を占有し続ける |
| IndexedDB にメタがあるが OPFS に重みがない | `artifact_status = present` なのに実行できないモデル |

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | 実体を先に書き、メタを後からコミット。孤児は起動時のGCで回収 |
| B | メタを先に `artifact_status = writing` で書き、実体の書き込み成功後に `present` へ更新 |
| C | 回復処理を持たず、不整合が起きたら該当モデルを壊れたものとして扱う |

### 推奨

**案A。** この順序なら「メタはあるが実体がない」状態は発生せず、残るのは容量を占有するだけの孤児ファイルになる。OPFS のファイル名を `artifact_id` / `blob_id` そのものにしてあるため、起動時に IndexedDB と突き合わせて回収できる。

案Bは中間状態を表す値がERモデルに増える（`artifact_status` に `writing` を追加する必要がある）。案Aなら**ERモデルの変更なしで済む。**

### 影響範囲

書き込み順序の規約、`StartupService` のGC処理、（案Bを採る場合）`Model.artifact_status` の値の追加。

### 決定

**案Aを採用**（2026-09-05）。実体を先に OPFS へ書き、メタを後から IndexedDB の単一トランザクションでコミットする。

この順序なら「メタはあるが実体がない」状態は発生せず、残るのは容量を占有するだけの孤児ファイルになる。OPFS のファイル名を `artifact_id` / `blob_id` そのものにしてあるため、起動時に IndexedDB と突き合わせて回収できる。**`artifact_status` に `writing` を追加する必要がなく、ERモデルの変更は発生しない。**

反映先: [04 §6.2](./04-storage-design.md#62-方針)

## 論点28 — スキーマ変更（マイグレーション）の方針

**ステータス: 決定済（2026-09-05）**

### 背景

IndexedDB はバージョン番号を上げたときの `upgradeneeded` でしかスキーマを変更できない。ストアやインデックスの追加はここでしか行えない。

本システムはユーザーのデータがローカルにしかなく、サーバー側で一括変換する手段がない。**古いバージョンのデータを持つ利用者が、いつアプリを開くか分からない。**

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | バージョンごとの移行関数を積み上げ、任意の古いバージョンから順に適用する |
| B | 後方互換のみ許す（列の追加のみ、削除・改名はしない） |
| C | A + B。構造の変更は移行関数、属性の追加は既定値で吸収する |

### 推奨

**案C。** 移行の仕組みは最初から用意しつつ、実際の変更はできるだけ後方互換に収める。

理由: エンティティ構成は確定している（フェーズ01）ため大きな構造変更は起きにくいが、インデックスの追加は運用中に必ず発生する。インデックス追加は移行関数が必要で、後方互換では吸収できない。

### 確認事項

- 移行に失敗した場合の扱い。エクスポートを促して初期化するか、旧バージョンのまま読み取り専用で開くか。

### 影響範囲

IndexedDB のバージョン管理、起動時処理、移行失敗時のUI。

### 決定

**案Cを採用**（2026-09-05）。移行の仕組みを最初から用意しつつ、属性の追加は既定値で吸収し、ストア・インデックスの追加は移行関数で行う。移行関数はバージョンごとに積み上げ、任意の古いバージョンから順に適用する。

**移行に失敗した場合は、旧スキーマのまま読み取り専用で開き、エクスポートを促す**（付随決定）。ローカルにしかデータがないため初期化は完全な喪失を意味する。移行に失敗しても、少なくともデータを取り出せる状態を維持する。閲覧とエクスポートのみを許可する読み取り専用モードのUI仕様は実装フェーズで詰める。

反映先: [04 §8](./04-storage-design.md#8-スキーマ変更マイグレーション)

## 論点29 — 参照カウントの管理方式

**ステータス: 決定済（2026-09-05）**

### 背景

方針16により、`ImageBlob` は「参照する `Image` がすべて論理削除済みで、かつ `dataset_items` / `inference_targets` からも参照されていない」ときだけ物理削除できる。この判定方法を決める必要がある。

### 選択肢

| 案 | 内容 | 利点 | 欠点 |

`RetentionService` / `StartupService` の削除処理、`ImageBlob` への `ref_count` 属性の要否。

### 決定

**案Aを採用**（2026-09-05）。削除時に都度集計する。`ImageBlob` に `ref_count` は持たせない。**ERモデルの変更は発生しない。**

## 論点31 — MLランタイムの構成

**ステータス: 決定済（2026-09-05）**

### 背景

`order.txt` §3.3 はブラウザ内での転移学習を要件としている。しかし**推論に最適なランタイムと、ブラウザ内学習ができるランタイムが一致しない可能性が高い。**

[03 §5](./03-system-architecture.md#port抽象インターフェース) で `InferenceEngine` と `TrainingEngine` を別の Port にしてあるため、異なるランタイムを割り当てることは構造上可能。ただし学習の入出力形式が推論用と異なると、系譜に変換が挟まる。

### 選択肢

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A | 単一ランタイムで推論と学習の両方を行う | モデル形式が1つに揃い、系譜に変換が挟まらない。Worker 内で重みを共有できる（論点19） | 推論性能で妥協する可能性がある |
| B | 推論用と学習用に別のランタイムを使う | それぞれ最適なものを選べる | 学習のたびに形式変換が発生。変換の失敗・精度劣化が新たな障害点になる。Worker のメモリに2つのランタイムが載る |
| C | 推論はブラウザ、学習は将来のGPUサーバーに寄せる | 推論を最適化できる。学習の実装リスクを回避 | **`order.txt` §3.3 のブラウザ内学習という前提を落とすことになる** |

### 推奨

**PoC（[05 §7](./05-technology-selection.md#7-決定前に検証すべきことpoc) の P2）の結果を見てから決める。**

- P2 で単一ランタイムでの転移学習が実用的な時間で動けば → 案A
- 動くが推論性能が許容できない場合 → 案B と案A の比較
- ブラウザ内学習が現実的でないと分かった場合 → 案C を要件側と再調整

案Bは形式変換が常時走る構成であり、方針7の `ModelDerivation.kind = convert` で記録はできるが、ユーザー体験としては「学習するたびに変換が走る」ことになる。積極的に選ぶ構成ではない。

### 影響範囲

`InferenceEngine` / `TrainingEngine` の実装、`ModelArtifact.format` の運用（論点32）、系譜に `convert` が現れるか、`order.txt` §3.3 の要件そのもの。

### 決定

**案Aを採用**（2026-09-05）。TensorFlow.js の単一構成とし、推論も学習も同じランタイムで行う。

[06 §4](./06-poc-results.md#p1--p4--worker-内の推論とバックエンド比較) で推論性能に差が出ず（ONNX/webgpu 27〜35ms、TF.js/webgl 25〜29ms）、[06 §5](./06-poc-results.md#5-p2--p3--ブラウザ内の転移学習) で TensorFlow.js による転移学習が成立した（200枚・30 epoch が合計9.7秒）。二本立てにする理由がなくなった。

モデル形式が1つに揃うため系譜に `convert` が挟まらず、単一 Worker 内で重みを共有できる。**`order.txt` §3.3 の前提を落とす必要もない。**

反映先: [05 §8.1](./05-technology-selection.md#81-論点31--tensorflowjs-の単一構成)

## 論点32 — モデル形式を1つに固定するか

**ステータス: 決定済（2026-09-05）**

### 背景

方針6で `ModelArtifact.format` を持たせてあるため、**ERモデルは複数形式の混在に耐えられる。** ただし構造上表現できることと、実際に混在させるべきかは別問題。

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | 1形式に固定する。他形式のモデルはインポート時に変換する |
| B | 複数形式を許し、`format` に応じて `ModelLoader` / `Preprocessor` / `Postprocessor` を切り替える |

### 推奨

**案A。** ただし論点31で案Bを採る場合は、必然的に案Bになる。

理由: 形式が1つなら、`ModelLoader` と前処理・後処理の実装が1組で済む。方針11で系譜が `Project` 内に閉じることも決まっているため、形式が混在する動機が乏しい。

### 影響範囲

`ModelLoader` / `Preprocessor` / `Postprocessor` の実装数、インポート機能の要否、論点31との依存関係。

### 決定

**案Aを採用**（2026-09-05）。アプリ内で扱うモデル形式は TF.js 形式のみとする。

論点33で YOLO 系を採るため変換は必要になるが、**変換は開発者側で事前に行い、Base Model として配信する。アプリ内に変換機能を持たない。** `ModelArtifact.format` は将来の形式追加に備えて残すが、当面は単一の値しか取らない。

反映先: [05 §8.2](./05-technology-selection.md#82-論点32--tfjs-形式に固定)

## 論点33 — Base Model のアーキテクチャ

**ステータス: 決定済（2026-09-05）**

### 背景

物体検知モデルのアーキテクチャ（YOLO 系、SSD、DETR 系など）を選ぶ。判断基準は**転移学習のしやすさ**が中心になる。

| 観点 | 判断基準 |
| --- | --- |
| クラス数の変更 | 検出ヘッドだけを差し替えてクラス数を変えられるか。方針1のクラス体系と直結する |
| 学習の計算量 | バックボーン凍結前提で、ブラウザで数分〜数十分に収まるか |
| 推論の計算量 | 1枚あたり数百ms以内に収まるか |
| モデルサイズ | [04 §9](./04-storage-design.md#9-容量の見積もり) の見積もりは1世代20MB。大きく超えると系譜の保持が破綻する |

`Training.hyperparameters` に `frozen_layers` を含めてある（方針3）ため、部分学習は表現できる。

### 推奨

**PoC（P3）で「検出ヘッドを差し替えてクラス数を変えられるか」を確認してから決める。** ここが成立しないアーキテクチャは、方針1のクラス体系と両立しない。

### 影響範囲

Base Model の作成作業、`Model.input_spec` の内容、`Training.hyperparameters` の具体的な項目、モデルサイズの見積もり。

### 決定

**YOLO 系を輸入する**（2026-09-05）。TF.js 形式に変換して Base Model として配信する。

推奨は「PoC の結果を見てから決める」だったが、検出性能を優先する判断で YOLO 系を採った。

**ただし [06 §5](./06-poc-results.md#5-p2--p3--ブラウザ内の転移学習) で確認できたのは MobileNet + 単一ボックス回帰という簡略化した構成での成立であり、YOLO 系を TF.js 形式に変換し、かつ検出ヘッドだけを学習できる形に分解できるかは未検証。** 実装フェーズの最初の作業として確かめる必要がある。成立しない場合はアーキテクチャの選び直しになる。

反映先: [05 §8.3](./05-technology-selection.md#83-論点33--yolo-系を輸入する)

## 論点34 — 実行バックエンドと COOP / COEP の要否

**ステータス: 決定済（2026-09-05）**

### 背景

WebGPU と WASM のどちらを前提にするか。**この選択は配信構成に波及する。**

WASM のマルチスレッド実行には `SharedArrayBuffer` が必要で、そのためには COOP / COEP ヘッダの設定が要る。論点22で「同一オリジンの静的ファイル配信」と決めたが、**ヘッダを設定できるホスティングが必要**になる可能性がある。

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | WebGPU を優先し、利用できない環境では WASM（シングルスレッド）にフォールバック |
| B | WASM を基準にし、COOP / COEP を設定してマルチスレッドを有効にする |
| C | WebGPU 必須。利用できない環境はサポート対象外とする |

### 推奨

**PoC（P4）で速度差と、COOP / COEP なしで動くかを確認してから決める。**

案Cは対応環境を絞りすぎる。案Aと案Bの比較は実測次第で、特に学習の実行時間に効く。

### 影響範囲

ホスティング要件（論点22の決定に追加される）、ランタイムのバックエンド設定、対応環境の範囲。

### 決定

**案Aを採用**（2026-09-05）。WebGPU を優先し、利用できない環境では WebGL に退避する。`@tensorflow/tfjs-backend-webgpu` を追加する。

[06 §4.3](./06-poc-results.md#43-読み取れること) のとおり **COOP / COEP は不要**で、論点22で決めた同一オリジンの静的配信にヘッダ要件は追加されない。WASM マルチスレッド化の利得（1,068ms → 468ms）より、WebGPU との差（27〜35ms）のほうが1桁以上大きいため。

PoC は WebGL で測定しており（推論25〜29ms、学習9.7秒/200枚）、**WebGL だけでも要求は満たせている。** 閉域環境ではブラウザが古い可能性があり、この退避は実際に使われる見込みが高い。

反映先: [05 §8.4](./05-technology-selection.md#84-論点34--webgpu-優先webgl-退避)

## 論点35 — フロントエンド構成

**ステータス: 決定済（2026-09-05）**

### 背景

言語・フレームワーク・ビルドツールを選ぶ。設計側からの要求は次のとおり。

- **TypeScript** — Port が5つ、エンティティが20あり、型で守る価値が大きい。
- **レイヤ構造を保てること** — [03 §4](./03-system-architecture.md#4-レイヤ構成) の5層と Port による依存性逆転が、フレームワークの流儀に潰されないこと。
- **Worker との相性** — ビルドツールが Worker のバンドルを素直に扱えること。

UIの規模は小さくない（アノテーション編集のキャンバス、系譜の可視化、学習の進捗表示）が、いずれも汎用的な要求であり、フレームワーク選定を強く縛るものではない。

### 確認事項

- チームの習熟度。設計上どれでも成立するため、実質的にはここで決まる。

### 影響範囲

ディレクトリ構成、ビルド設定、UIコンポーネントの実装方針。他の論点とは独立。

### 決定

**TypeScript + React + Vite**（2026-09-05）。判断は「閉域環境へ移植する」という前提を考慮して委ねられた。

閉域環境では人員の入れ替えや長期保守が難しくなりやすく、**知っている人が多い技術を使う価値が相対的に高い**ためReactを採る。あわせて閉域向けの制約を定めた。

- 実行時に外部ホストへ取りに行かない。CDN・Webフォント・外部APIを一切使わない。**モデルの重みも配信物に同梱する。**
- 依存はロックファイルで固定し、`npm ci` がオフラインで通る状態にする。
- React は表示層に閉じ込め、Application 以下は素の TypeScript で書く。UIフレームワークへの依存を UI Layer の外に漏らさない。

閉域環境の具体的な条件は論点36で確定させる。

反映先: [05 §8.5](./05-technology-selection.md#85-論点35--typescript--react--vite)

## 論点36 — 閉域環境の条件

**ステータス: 決定済（2026-09-05）**

### 背景

論点35の回答として「閉域に移植する」という前提が新たに示された。これは技術選定・配信構成・実装計画のすべてに効く制約であり、条件を確定させないと実装計画を組めない。

論点22で「同一オリジンの静的ファイル配信」を選んでいたため設計そのものは閉域と整合しているが、次の点は未確定。

1. **モデル重みの同梱** — PoC では TensorFlow.js のモデル（coco-ssd / mobilenet）が実行時に `storage.googleapis.com` から重みを取得していた。**この経路は閉域では成立しない。** Base Model の重みは配信物に同梱する必要があり、初回ロードのサイズと配信方法に影響する。
2. **ビルドと依存パッケージの調達** — 閉域内でビルドするのか、外でビルドした成果物を持ち込むのか。前者なら社内ミラーか `node_modules` の持ち込みが要る。
3. **ブラウザのバージョン** — 閉域環境ではブラウザが固定・制限されていることがある。WebGPU・OPFS・`createSyncAccessHandle` が使えるかで、論点25（実体の格納先）と論点34（バックエンド）の退避経路が実際に必要になるかが決まる。
4. **モデルの更新手段** — 方針18で「更新版は別のモデルとして追加」と決めたが、閉域では配信物の差し替えが手作業になる可能性がある。

### 確認事項

- 閉域環境のブラウザは何か。バージョンは固定されているか。
- 閉域内でビルドするか、成果物を持ち込むか。社内 npm ミラーはあるか。
- 配信物のサイズ上限や、持ち込み手段（メディア・審査）の制約はあるか。
- 開発は閉域外で行い、リリース時のみ移植する運用か。

### 影響範囲

Base Model の同梱方式と初回ロードサイズ、ビルド構成、対応ブラウザの下限、論点25・34の退避経路の要否、実装計画（07）の作業順序。

### 決定

（2026-09-05）

| 条件 | 決定 |
| --- | --- |
| ブラウザ | **新しめの Chrome / Edge が使える。** WebGPU・OPFS・`createSyncAccessHandle` を前提にしてよい |
| ビルド | **閉域外でビルドし、成果物を持ち込む。** 社内 npm ミラーや `node_modules` の持ち込みは不要 |
| 移植の時期 | **最初から閉域前提で作る。** MVP の段階から外部取得ゼロで構成する |

ここから導かれること。

- **配信物は静的ファイル一式**（アプリ本体 + Base Model の重み）。ビルド時にモデルの重みを `dist/` へ取り込む工程が要る。
- **方針18（メタは初回全件登録、重みは遅延取得）はそのまま成立する。** 遅延取得の相手が外部ホストではなく同梱された同一オリジンのファイルになるだけで、論点22の決定とも整合する。
- **論点25の `BlobStore` の IndexedDB フォールバックと、論点34の WebGL 退避は「保険」に格下げできる。** 実装は残すが、MVP の必須項目からは外してよい。
- 外部取得ゼロを最初から守るため、**CDN・Webフォント・外部APIを使わないことを実装ルールとして最初に定める。** 後から剥がすより安い。

反映先: [05 §1.2](./05-technology-selection.md#12-閉域環境への移植前提の追加)

## 論点37 — MVP に `Project` を含めるか

### 背景

論点16でプロジェクト単位の完全分離を決め、Base Model を除くほぼ全エンティティが `project_id` を持つ構造になった。一方 MVP のスコープは論点30で「推論 + 履歴」と決めており、プロジェクト管理は含まれていない。

| --- | --- |

| B | 含めない。M4 で全ストアのマイグレーションを行う |
| C | `ProjectManager`（作成・切替・削除）まで MVP に入れる |

### 影響範囲

## 論点39 — 外部取得ゼロの担保方法

**ステータス: 決定済（2026-09-05）**

### 背景

論点36で「最初から閉域前提で作る」と決めた。CDN・Webフォント・外部APIを使わないという実装ルールは定めたが、**人手のレビューに頼ると必ず漏れる。** 漏れは閉域へ持ち込んで初めて発覚し、そこでの調査は最も高くつく。

### 選択肢

| 案 | 内容 |
| --- | --- |
| A | CI でビルド成果物（`dist/`）を grep し、許可リスト外の外部URLがあれば落とす |
| B | CSP（`connect-src 'self'` 等）で実行時にブラウザ側から禁止する |
| C | 依存パッケージに CDN・Webフォント参照が混ざっていないかをビルド前に検査する |
| D | ネットワークを切った状態で起動〜推論まで通ることを確認する手順を用意する |

### 影響範囲

CI の構成、リリース前チェックの手順、M0 の作業内容。

### 決定

（2026-09-05）**案A + 案D の二段構え。**

| 手段 | 位置づけ |
| --- | --- |
| CI での成果物 grep | **機械的な防止線。** ビルド後の実物を見るため、依存の奥に埋まった参照も拾える。許可リスト外の外部URLで CI を落とす |
| オフライン動作確認の手順化 | **実地の検証。** ネットワークを切って起動から推論まで通ることをリリース前チェックに入れる。grep が見逃す動的に組み立てられたURLは、ここで捕まえる |

grep は静的な文字列しか見られず、オフライン確認は自動で回らない。**片方だけでは穴が残るため両方を置く。**

案B（CSP）と案C（依存の静的チェック）は今回は採用しない。案A で成果物を直接検査するため案Cは重複度が高く、案Bは必要になった時点で追加できる（**保険として設計には残す**）。
