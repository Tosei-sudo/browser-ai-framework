## 1. このドキュメントの位置づけ

`order.txt` が意図的に保留してきた技術選定を行う。設計3フェーズが完了し、「何を管理し、どう配置し、どこに保存するか」が確定したため、それを満たす技術を選べる状態になった。

扱うのは以下。

- MLランタイム（推論・学習）
- モデル形式
- Base Model のアーキテクチャ
- 実行バックエンド（WebGPU / WASM）
- フロントエンド構成

### 1.1 検証を経た決定であること

当初このドキュメントは未検証の候補整理として書かれた。その後 §7 の検証（PoC）を実施し、[06-poc-results.md](./06-poc-results.md) の結果をもとに論点31〜35を決定した。決定内容は §8 にまとめている。

### 1.2 閉域環境への移植（前提の追加）

本システムは**閉域環境（外部ネットワークに接続できない環境）へ移植する**前提が後から加わった。これは技術選定の全体に効く制約であり、次を意味する。

- **実行時に外部ホストからリソースを取得してはならない。** アプリ本体・モデルの重み・フォントを含め、すべて同一オリジンから配信する。
- **ビルドも閉域内で完結できる必要がある**（またはビルド成果物を持ち込む運用にする）。依存パッケージの調達方法を決めておく。
- **ブラウザのバージョンが固定・制限されている可能性がある。** WebGPU・OPFS など新しめのAPIが使えない環境を想定した退避が要る。

論点22で「同一オリジンの静的ファイル配信」を選んでいたため、設計そのものは閉域と整合している。ただし**PoC では TensorFlow.js のモデル（coco-ssd / mobilenet）が実行時に `storage.googleapis.com` から重みを取得しており、この経路は閉域では成立しない。** Base Model の重みは配信物に同梱する。

具体的な環境条件は論点36で確定させる。

## 2. MVP スコープ（決定済み）

**推論 + 履歴まで**（論点30）。Base Model を選んで画像を推論し、結果を履歴として残すところまでを最初の目標とする。学習は含めない。

理由: ストレージ・Port 構成・推論経路を先に検証でき、最もリスクの高い学習を後回しにできる。

ただし**技術選定では学習まで見据える必要がある。** MVP に学習が入らないからといって推論だけで最適なランタイムを選ぶと、学習を実装する段階で作り直しになる。これが §3 の中心的な論点。

## 3. 前提となる制約

設計フェーズで確定した内容のうち、技術選定を縛るもの。

| 制約 | 出典 | 選定への影響 |
| --- | --- | --- |
| 転移学習をブラウザ内で実行する | `order.txt` §3.3 | 学習可能なランタイムが必要。最大の制約 |
| Port は推論・学習・前処理・後処理・ロードの5つ | [03 §5](./03-system-architecture.md#port抽象インターフェース) | ランタイムを跨いだ組み合わせが構造上は可能 |
| 単一 ML Worker に集約 | 論点19 | ランタイムが Worker で動くことが必須 |
| 重みは OPFS に保存 | 論点25 | `ArrayBuffer` として読み書きできる形式であること |
| `Model.input_spec` に前処理仕様を持つ | 方針15 | 前処理をランタイム任せにせず、こちらで制御できること |
| `ModelArtifact.format` を持つ | 方針6 | **複数のモデル形式を構造上は表現できる** |
| モデル系譜を追跡する | 方針7 | 転移学習の入出力が同じ形式でないと、系譜に `convert` が挟まる |

最後の2つが重要で、**ERモデルは複数形式の混在に耐えられる設計になっている。** これは選択肢を広げるが、混在させるべきかは別の判断（論点32）。

## 4. MLランタイム

### 4.1 候補

| 候補 | 推論 | ブラウザ内学習 | 備考 |
| --- | --- | --- | --- |
| ONNX Runtime Web | 得意。WASM / WebGPU バックエンド | 限定的。Web 向けの学習サポートは要検証 | 推論用途では最有力 |
| TensorFlow.js | 可能 | **学習APIが揃っており、転移学習の実績も多い** | 物体検知モデルの入手性は要検証 |
| Transformers.js | 可能（ONNX ベース） | なし | 推論特化。物体検知も扱えるが学習は不可 |
| WebNN | 標準化途上 | — | 現時点で前提にできない |

### 4.2 中心的な論点

**推論に最適なランタイムと、ブラウザ内学習ができるランタイムが一致しない可能性が高い。** これが技術選定の最大の分岐点になる（論点31）。

Port を5つに分けてあるため（[03 §5](./03-system-architecture.md#port抽象インターフェース)）、`InferenceEngine` と `TrainingEngine` に別のランタイムを割り当てることは**構造上は可能**。ただし次の問題が生じる。

```text
Model A（ONNX 形式・推論用ランタイム）
   │
   │ 転移学習（学習用ランタイム）
   ↓
Model B（学習用ランタイムの形式）
   │
   │ 推論するには変換が必要
   ↓
Model B'（ONNX 形式）
```

系譜に `ModelDerivation.kind = convert` が挟まる。方針7でこの `kind` を用意してあるため**記録はできる**が、ユーザーから見ると「学習するたびに変換が走る」ことになり、変換の失敗や精度劣化が新たな障害点になる。

## 5. モデル形式とアーキテクチャ

### 5.1 モデル形式

`ModelArtifact.format` があるため複数形式を持てるが、実際に混在させるかは判断が要る（論点32）。

混在させる場合、`Model.label_set_id`（方針1）と `input_spec`（方針15）が形式に依存しない抽象になっているかを確認する必要がある。クラス体系と前処理仕様をERモデル側で持つ設計にしてあるため、ここは比較的耐性がある。

### 5.2 Base Model のアーキテクチャ

物体検知モデルの選択は、**転移学習のしやすさ**で決まる（論点33）。

| 観点 | 判断基準 |
| --- | --- |
| クラス数の変更 | 検出ヘッドだけを差し替えてクラス数を変えられるか。方針1のクラス体系（`LabelSet` の派生）と直結する |
| 学習の計算量 | ブラウザで数分〜数十分に収まるか。バックボーンを凍結する前提で見積もる |
| 推論の計算量 | 1枚あたり数百ms以内に収まるか |
| モデルサイズ | §04 の見積もりでは1世代20MBを想定。これを大きく超えると系譜の保持が破綻する |

`Training.hyperparameters` に `frozen_layers` を含めてある（方針3）ため、バックボーン凍結のような部分学習は表現できる。

## 6. 実行バックエンドとフロントエンド構成

### 6.1 実行バックエンド

WebGPU と WASM のどちらを前提にするか（論点34）。

**この選択は配信構成に波及する。** WASM のマルチスレッド実行には `SharedArrayBuffer` が必要で、そのためには COOP / COEP ヘッダの設定が要る。論点22で「同一オリジンの静的ファイル配信」と決めたが、**COOP / COEP が必要なら、単純な静的ホスティングでは足りない可能性がある**（ヘッダを設定できるホスティングが必要）。

論点22の決定そのものは変わらないが、ホスティングの要件が追加される。

### 6.2 フロントエンド構成

言語・フレームワーク・ビルドツールの選定（論点35）。

設計側からの要求は次のとおり。

- **TypeScript** — Port が5つ、エンティティが20あり、型で守る価値が大きい。
- **レイヤ構造を保てること** — [03 §4](./03-system-architecture.md#4-レイヤ構成) の5層と Port による依存性逆転が、フレームワークの流儀に潰されないこと。
- **Worker との相性** — ビルドツールが Worker のバンドルを素直に扱えること。

UIの規模は小さくない（アノテーション編集のキャンバス、系譜の可視化、学習の進捗表示）が、いずれも汎用的な要求であり、フレームワーク選定を強く縛るものではない。

## 7. 決定前に検証すべきこと（PoC）

§1.1 のとおり、以下は実際に動かして確認しないと判断できない。**論点31〜34は、この検証の結果を見てから決めることを推奨する。**

| # | 検証項目 | 何が分かるか | 関連 |
| --- | --- | --- | --- |
| P1 | 候補ランタイムで物体検知モデルの推論が Worker 内で動くか。1枚あたりの実行時間 | 推論ランタイムの候補が絞れる | 論点31 |
| P2 | 候補ランタイムでブラウザ内の転移学習が実際に動くか。数百枚の学習にかかる時間 | **単一ランタイムで完結できるかが決まる** | 論点31 |
| P3 | 検出ヘッドを差し替えてクラス数を変えられるか | Base Model のアーキテクチャが絞れる | 論点33 |
| P4 | WebGPU 利用時と WASM 利用時の速度差、および COOP / COEP なしで動くか | バックエンドとホスティング要件が決まる | 論点34 |
| P5 | 学習済み重みを `ArrayBuffer` として取り出し、OPFS に保存して読み戻せるか | [04](./04-storage-design.md) の前提が成立するか確認できる | 論点25 |

P2 が最も重要で、結果次第では `order.txt` §3.3 の「ブラウザ内での転移学習」という前提そのものを見直す必要が出る。その場合は [03 §2](./03-system-architecture.md#2-前提の整理--サーバーを持たないの定義) で拡張点として定義した GPU サーバー学習が選択肢になる。

## 8. 設計上の論点

決定ログの通し番号を継続する。詳細と選択肢は [02-open-decisions.md](./02-open-decisions.md) を参照。

| # | 論点 | 決定 |
| --- | --- | --- |
| 30 | MVP スコープ | 推論 + 履歴まで |
| 31 | MLランタイムの構成 | **TensorFlow.js の単一構成。** 推論も学習も同じランタイムで行う |
| 32 | モデル形式 | **TF.js 形式に固定。** YOLO の変換は開発者側で事前に行い、Base Model として配信する |
| 33 | Base Model のアーキテクチャ | **YOLO 系を輸入する**（TF.js 形式へ変換して提供） |
| 34 | 実行バックエンド | **WebGPU を優先し、使えない環境では WebGL に退避** |
| 35 | フロントエンド構成 | **TypeScript + React + Vite。** 閉域前提の制約を §8.5 に定める |
| 36 | 閉域環境の条件 | 未決（§1.2 を参照） |

### 8.1 論点31 — TensorFlow.js の単一構成

[06 §4](./06-poc-results.md#p1--p4--worker-内の推論とバックエンド比較) で推論性能に差が出ず、[06 §5](./06-poc-results.md#5-p2--p3--ブラウザ内の転移学習) で学習が成立したため、二本立てにする理由がなくなった。

- モデル形式が1つに揃い、**系譜に `ModelDerivation.kind = convert` が挟まらない**（方針7）。
- 単一 Worker 内で重みを共有できる（論点19）。
- §4.2 で「技術選定の最大の分岐点」とした問題は、**発生しない。**

### 8.2 論点32 — TF.js 形式に固定

アプリ内で扱うモデル形式は TF.js 形式のみとする。論点33で YOLO 系を採るため変換は必要になるが、**変換は開発者側で事前に行い、Base Model として配信する。** アプリ内に変換機能を持たない。

`ModelArtifact.format` は残す（方針6）。将来の形式追加に備えた余地であり、当面は単一の値しか取らない。

### 8.3 論点33 — YOLO 系を輸入する

[06 §5.3](./06-poc-results.md#53-読み取れること) でヘッド差し替えによるクラス数変更は成立したが、それは MobileNet + 単一ボックス回帰という簡略化した構成での確認である。

**YOLO 系を TF.js 形式に変換し、かつ検出ヘッドだけを学習できる形に分解できるかは未検証。** 実装フェーズの最初の作業として確かめる必要がある（§9）。

### 8.4 論点34 — WebGPU 優先、WebGL 退避

`@tensorflow/tfjs-backend-webgpu` を追加し、利用できる環境では WebGPU を使う。使えない環境は WebGL に退避する。

[06 §4.3](./06-poc-results.md#43-読み取れること) のとおり **COOP / COEP は不要**で、論点22で決めた同一オリジンの静的配信にヘッダ要件は追加されない。

なお PoC は WebGL で測定しており（推論25〜29ms、学習9.7秒/200枚）、**WebGL だけでも要求は満たせている。** WebGPU の利得は未検証であり、退避先が主役になっても支障はない。閉域環境ではブラウザが古い可能性があるため、この退避は実際に使われる見込みが高い。

### 8.5 論点35 — TypeScript + React + Vite

設計上はどの選択でも成立するため、閉域移植の制約と人員の確保しやすさで決める。

| 要求 | 満たし方 |
| --- | --- |
| TypeScript | Port 5つ・エンティティ20を型で守る |
| レイヤ構造を保つ | React は表示層に閉じ込め、Application 以下は素の TypeScript で書く。UIフレームワークへの依存を UI Layer の外に漏らさない |
| Worker との相性 | Vite は Worker のバンドルを標準で扱える |
| **閉域での実行** | **実行時に外部ホストへ取りに行かない。** CDN・Webフォント・外部APIを一切使わない。モデルの重みも配信物に同梱する |
| **閉域でのビルド** | 依存はロックファイルで固定し、`npm ci` がオフラインで通る状態にする（社内ミラー、または `node_modules` ごと持ち込む） |

React を選ぶのは、閉域環境では人員の入れ替えや長期保守が難しくなりやすく、**知っている人が多い技術を使う価値が相対的に高い**ため。アノテーション編集のキャンバスは React の外（素の Canvas API）で書くことになるが、これはどのフレームワークでも同じ。
