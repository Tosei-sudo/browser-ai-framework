## 3. P5 — OPFS への保存・読み戻し

### 3.1 結果

**すべての項目で成立した。**[04-storage-design.md](./04-storage-design.md) の前提は維持できる。

| 項目 | 結果 |
| --- | --- |
| OPFS（`navigator.storage.getDirectory`） | 利用可 |
| `createSyncAccessHandle`（Worker） | 利用可 |
| `ArrayBuffer` の往復と整合性（SHA-256 で照合） | 5MB / 20MB / 60MB すべて一致 |
| ディレクトリ列挙 | 可能。ファイル名とサイズを取得できた |
| 削除後の使用量 | 0MB に戻った |

### 3.2 読み書き性能

| 方式 | サイズ | write | read |
| --- | --- | --- | --- |
| メインスレッド（`createWritable`） | 5MB | 19ms | 7ms |
| | 20MB | 49ms | 14ms |
| | 60MB | 84ms | 30ms |
| Worker（`createSyncAccessHandle`） | 5MB | 13ms | 6ms |
| | 20MB | 90ms | 12ms |
| | 60MB | 63ms | 35ms |

**[04 §9](./04-storage-design.md#9-容量の見積もり) で想定した「1世代20MB」のモデルは、読み書き100ms未満で扱える。** 容量見積もりの範囲では、ストレージI/Oがボトルネックになる兆候はない。

メインスレッドと Worker で有意な差は出なかった。**Worker を使う理由は性能ではなく、[03 の論点19](./03-system-architecture.md#実行スレッド構成論点19) で決めた実行スレッド構成に従うため**という位置づけで問題ない。

### 3.3 容量

`navigator.storage.estimate()` の `quota` は **10,240MB（10GB）** だった。

[04 §2.2](./04-storage-design.md#22-容量の上限) では「数百MB〜数GB程度の幅がある」と書いたが、この環境ではそれを上回った。ただしブラウザ・OS・ディスク空き容量に依存する点は変わらないため、**特定の容量を前提としない方針は維持する。**

### 3.4 重要な発見 — `persist()` が拒否された

```text
persisted (要求前): false
persist() の結果:   false
```

**[04 §2.1](./04-storage-design.md#21-データを捨てないを脅かす最大のリスク) で懸念した状況が、実際に再現した。**

この環境では永続化が許可されず、ブラウザによる自動削除の対象のままである。localhost かつサイトへの利用実績がない状態のため、本番配信で利用を重ねれば許可される可能性はあるが、**「拒否されうる」ではなく「実際に拒否される」ことが確認できた。**

論点26で決めた方針（起動時に要求し、拒否時は警告してエクスポートを促す。操作はブロックしない）は妥当だったが、次の点を補強する必要がある。

- 警告は「まれな異常系」ではなく**初期状態として起こりうるもの**として扱う。初回起動時に拒否されるのが通常だと考えて、UIの導線を設計する。
- エクスポート機能（方針17）の実装優先度は、想定よりさらに高い。MVP スコープ（推論 + 履歴）には含まれていないが、**学習機能を出す前には必須**と位置づける。

## 4. P1 / P4 — Worker 内の推論とバックエンド比較

### 4.1 検証の構成

| 項目 | 内容 |
| --- | --- |
| ONNX Runtime Web | 1.29.0。モデルは `Xenova/yolos-tiny`（25.0MB、入力 512×512） |
| TensorFlow.js | 4.22.0 + `@tensorflow-models/coco-ssd` 2.2.3（`lite_mobilenet_v2`） |
| 実行場所 | すべて Worker 内（論点19の構成に合わせた） |
| 測定 | ウォームアップ1回の後、5回実行して中央値 |
| 入力画像 | 合成画像（実写ではない） |

### 4.2 結果

**4つの組み合わせすべてが Worker 内で動作した。** ランタイムのロードも推論も、メインスレッドを使わずに完結する。

COOP / COEP なし（`crossOriginIsolated = false`, `SharedArrayBuffer` 利用不可）:

| ランタイム / バックエンド | load | infer（中央値） | min / max |
| --- | --- | --- | --- |
| ONNX Runtime Web / wasm | 846ms | **1,068ms** | 915 / 1,096 |
| ONNX Runtime Web / webgpu | 417ms | **35ms** | 25 / 45 |
| TensorFlow.js / webgl | 8,308ms | **29ms** | 16 / 34 |
| TensorFlow.js / cpu | 4,065ms | **4,158ms** | 3,968 / 4,185 |

COOP / COEP あり（`crossOriginIsolated = true`, `SharedArrayBuffer` 利用可）:

| ランタイム / バックエンド | load | infer（中央値） | min / max |
| --- | --- | --- | --- |
| ONNX Runtime Web / wasm | 832ms | **468ms** | 428 / 480 |
| ONNX Runtime Web / webgpu | 343ms | **27ms** | 25 / 35 |
| TensorFlow.js / webgl | 2,927ms | **25ms** | 21 / 26 |
| TensorFlow.js / cpu | 3,473ms | **3,545ms** | 3,147 / 3,932 |

### 4.3 読み取れること

**① GPU 系バックエンドなら推論は 25〜35ms で済む。**

`Model.input_spec` の 512×512 で1枚あたり30ms前後であり、[05](./05-technology-selection.md) で置いた「1枚あたり数百ms以内」の基準を大きく下回る。**推論性能は技術選定の制約にならない。**

**② CPU 系バックエンドは実用にならない。**

ONNX Runtime Web / wasm が1秒、TensorFlow.js / cpu が4秒。GPU が使えない環境へのフォールバックとしては成立するが、常用は難しい。

**③ COOP / COEP は必須ではない（論点34）。**

`SharedArrayBuffer` による WASM マルチスレッド化で、ONNX Runtime Web / wasm は 1,068ms → 468ms と 2.3倍速くなった。しかし**WebGPU の 27〜35ms とは1桁以上の差があり、WebGPU が使えるならこの差は問題にならない。**

したがって COOP / COEP は「WASM フォールバック時の改善策」であって、前提条件ではない。**論点22で決めた同一オリジンの静的配信に、ヘッダ設定の要件を追加する必要はない。**

**④ 推論性能でランタイムを選ぶ理由は乏しい。**

ONNX Runtime Web / webgpu（27〜35ms）と TensorFlow.js / webgl（25〜29ms）はほぼ同等。モデルもタスクも異なるため厳密な比較ではないが、**少なくとも「推論性能を理由に ONNX Runtime Web を選ぶ」という論拠は成立しない。** 論点31（単一ランタイムか二本立てか）の判断は、P2（学習が動くか）の結果で決めてよい。

### 4.4 検証できていないこと

**検出結果の正しさは確認できていない。** 合成画像を入力としたため検出は0件で、これは期待どおりだが、前処理・後処理（`Preprocessor` / `Postprocessor`、論点20）が正しく実装できているかの裏付けにはならない。

推論そのものは動いており、出力テンソルの形状も想定どおり（`logits` と `pred_boxes`）なので、**P1 の目的である「Worker 内で推論が動くか、1枚あたりの時間はどれくらいか」は満たしている。** 検出の正しさは実写画像での確認が必要で、`/p1-inference/` の画像選択から実行できる。

## 5. P2 / P3 — ブラウザ内の転移学習

### 5.1 検証の構成

| 項目 | 内容 |
| --- | --- |
| データセット | `datitran/raccoon_dataset`（MIT、200枚、VOC アノテーション、1クラス） |
| バックボーン | MobileNet v2（`@tensorflow-models/mobilenet` 2.1.1）。**凍結** |
| ヘッド | Dense 128 → Dropout → Dense 4（sigmoid）。単一ボックス回帰、164,484 パラメータ |
| 損失 | MSE。評価は cxcywh の平均 IoU |
| 分割 | train 160 / val 40 |
| 実行場所 | すべて Worker 内（バックエンド webgl） |

バックボーンを凍結しているため特徴量は不変であり、200枚分を先に計算してからヘッドを学習した。実アプリでも同じ最適化ができる。

### 5.2 結果

**ブラウザ内での転移学習は成立した。**

| 項目 | 値 |
| --- | --- |
| バックボーンのロード | 5,745ms |
| 特徴量の事前計算（200枚） | 2,187ms（1枚あたり **10.9ms**、次元 1280） |
| ヘッドの学習（30 epoch） | 1,750ms（1 epoch 中央値 **21ms**） |
| **合計** | **9.7秒** |
| loss | 0.03451 → 0.02176 |
| val loss | 0.01663 → 0.01624 |
| 平均IoU（検証40枚） | **0.35 → 0.629** |
| ピーク時のメモリ | tensors 128 / 17.2MB |
| 解放後のメモリ | tensors 118 / 14.6MB |
| 重みの取り出しと OPFS 保存 | 642.5KB、往復のバイト数一致 |

### 5.3 読み取れること

**① 転移学習は実用的な時間で回る。**

200枚・30 epoch が **9.7秒**。`order.txt` §3.3 の「ユーザーがブラウザ上で転移学習を実行する」という前提は、**凍結バックボーン構成であれば十分に成立する。** [05 §7](./05-technology-selection.md#7-決定前に検証すべきことpoc) で「結果次第では前提の見直しが必要」としたが、**その必要はない。**

支配的なのはバックボーンのロード（5.7秒）で、学習そのものは2秒に満たない。ロードは初回だけであり、[04](./04-storage-design.md) の設計どおり重みをキャッシュすれば2回目以降は消える。

**② 学習は実際に進んだ。**

平均IoU が 0.35 → 0.629 に改善した。単一ボックス回帰という簡略化したヘッドでの数値であり検出器としての精度ではないが、**「勾配が流れ、重みが更新され、汎化性能が上がる」ことは確認できた。**

**③ メモリは問題にならない。**

ピークで 17.2MB。ブラウザのタブが扱う量として小さく、[03 の論点19](./03-system-architecture.md#実行スレッド構成論点19)で「メモリ上限が最大の制約」として単一 Worker に集約した判断は、**この規模では過剰なほど安全側**だった。ただしバックボーンまで学習する構成では前提が変わる（§5.4）。

**④ ヘッドの差し替えでクラス数を変えられる（P3）。**

COCO 91クラスで学習された MobileNet を土台に、1クラスの新しいヘッドを付けて学習できた。[方針1](./01-conceptual-er-model.md#方針1-クラス体系を独立エンティティとして管理する論点01)の「`LabelSet` を派生させてクラスを増減する」という運用は、技術的に成立する。

**⑤ 学習した重みは取り出して保存できる。**

`tf.io.withSaveHandler` で `ArrayBuffer` を取り出し、OPFS に書いてバイト数が一致した。[04](./04-storage-design.md) の `ModelArtifact` の扱いと、[論点27](./02-open-decisions.md#論点27--indexeddb--opfs-間の不整合の回復方式)で決めた「実体を先に書く」順序が、そのまま実装できる。

### 5.4 検証できていないこと

**① バックボーンまで学習する構成は測っていない。**

今回は完全に凍結した。`Training.hyperparameters.frozen_layers`（方針3）で一部を解凍する構成では、逆伝播がバックボーンを通るため**計算量もメモリも桁違いに増える。** その構成を要件に含めるなら、別途測る必要がある。

**② ヘッドは本物の検出器ではない。**

単一ボックス回帰であり、アンカー・複数物体・NMS を含まない。実際の検出ヘッドはパラメータ数も計算量も増えるが、**支配項は特徴量計算（10.9ms/枚）であり、ヘッドの学習（21ms/epoch）が数倍になっても全体の結論は変わらない。**

**③ 規模は200枚。**

特徴量計算は枚数に比例するため、1,000枚なら約11秒、5,000枚なら約55秒と見込める。ヘッドの学習時間は無視できる範囲。**数千枚規模でも1分程度**で、実用の範囲に収まる。

## 6. 論点への影響

| 論点 | 影響 |
| --- | --- |
| 25（実体の格納先） | **決定を裏付けた。** OPFS で成立し、フォールバックは当面不要と見込める |

**設計ドキュメントの変更が必要な箇所はない。**

- 05 §4.2 で「推論に最適なランタイムと学習できるランタイムが一致しない可能性」を最大の分岐点としたが、**TensorFlow.js が両方をこなしたため、この分岐は発生しない。**

## 7. R1 — YOLO の TF.js 変換とヘッド分解（2026-09-05 追加）

論点33で YOLO 系の輸入を決めたが、P2 / P3 で確認できたのは MobileNet + 単一ボックス回帰という
簡略化した構成での成立だった。YOLO 系で同じことができるかは未検証で、
[07 §3](./07-implementation-plan.md#3-最初に潰すべきリスク) の **R1** として切り出していた。

### 7.1 検証の構成

変換は開発者側の作業なので Docker で行う（論点32・36）。コードは
[`tools/model-conversion/`](../../tools/model-conversion/README.md)。

```text
yolov8n.pt --(ultralytics)--> ONNX --(onnx2tf)--> SavedModel --(freeze)--> GraphDef
           --(tensorflowjs_converter)--> TF.js GraphModel
```

2種類を書き出す。

| 成果物 | 内容 | 用途 |
| --- | --- | --- |
| `yolov8n_tfjs` | 検出ヘッドまで含めた完成モデル | 推論（M2・M3） |
| `yolov8n_backbone_tfjs` | **検出ヘッド（`Detect`）を `Identity` に差し替えたもの** | 転移学習の土台（M5） |

ブラウザ側の確認は [`poc/p6-yolo/`](../../poc/README.md)。Worker 内で TF.js（WebGL）を使い、
完成モデルの推論、特徴量の取り出し、ヘッドだけの学習を順に実行する。

### 7.2 結果

| 項目 | 結果 |
| --- | --- |
| TF.js 形式への変換 | **成立。** GraphModel（重み 12.8 MB / 4 シャード、486 ノード） |
| 完成モデルの出力 | `[1, 84, 8400]`（84 = 4 box + 80 class、8400 = 全アンカー） |
| 推論時間 | **26.6 ms**（640×640、WebGL、5回の中央値。合成入力） |
| ヘッドの分離 | **成立。** バックボーン + ネックを別モデルとして書き出せた（重み 9.0 MB） |
| 特徴量 | P3 `[1,80,80,64]` / P4 `[1,40,40,128]` / P5 `[1,20,20,256]` |
| ヘッドだけの学習 | **成立。** loss 0.2050 → 0.0847（10ステップ） |
| 学習速度 | 1ステップ 129 ms（16サンプル / バッチ4、P5 のみ、ヘッド 147,910 パラメータ） |
| 学習した重みの取り出し | 成立（4テンソル / 0.6 MB） |
| メモリ | 実行後の保持 1.1 MB（リークなし） |

### 7.3 読み取れること

**論点33（YOLO 系の輸入）は成立する。選び直しは不要。**

- **推論 26.6 ms は P1 の coco-ssd（25〜29ms）と同等。** YOLOv8n を入れても実行時間の桁は変わらない。
- **転移学習の構成は P2 / P3 と同じ形になる。** バックボーン + ネックを凍結した特徴抽出器として使い、
  その上に TF.js 側で作った新しいヘッドを載せて学習する。方針3 の `frozen_layers` は
  「どこで切って書き出すか」という**変換時の選択**として実現される。
- **配信サイズは 12.8 MB（完成モデル）+ 9.0 MB（バックボーン）。** 閉域へ同梱しても現実的な大きさ
  （論点36）。ただし学習を使う構成では両方を配る必要があり、初回ロードの設計に効く。

### 7.4 変換で詰まった点（再現のための記録）

同じ経路を再構築するとき、次の4点は必ず踏む。すべて
[`tools/model-conversion/Dockerfile`](../../tools/model-conversion/Dockerfile) と
`convert.py` に対処を書いてある。

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| ONNX 書き出しで segfault（exit 139） | ultralytics が opset 9 を選び、torch 側の版変換が落ちる | `opset=18` を明示する |
| 同じく segfault | torch 2.14 のエクスポータ | torch 2.4.1 に固定する |
| tfjs 変換器が protobuf の版で落ちる | `tflite_support` は protobuf 3.20、変換器は新しい版を要求する | 変換器だけ別の venv に隔離する |
| ヘッドを外したモデルの読み込みが壊れる | onnx2tf が簡約前の ONNX を誤変換する | `fuse()` + `onnxslim` を通してから変換する |

`Detect` を `Identity` に差し替えるときは、`f`（入力元レイヤ）と `i`（インデックス）を
引き継ぐ必要がある。引き継がないと ultralytics の `_predict_once` がスキップ接続を解決できない。

### 7.5 検証できていないこと

- **本物の検出ヘッドではない。** 学習させたのは畳み込み2層の簡易ヘッドで、DFL や
  タスク整合の割り当ては入っていない。実際の精度と学習時間はこれより重い（持ち越し事項#19）。
- **実データでの精度は測っていない。** 合成入力での成立性の確認に留まる。
- **バックボーンの部分解凍は試していない**（持ち越し事項#18）。
- **WebGPU では測っていない。** WebGL での測定のみ（持ち越し事項#20 は M3 で扱う）。
