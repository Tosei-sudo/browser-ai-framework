# ブラウザベース画像物体検知アプリ

## 設計方針・作業指示書

### 1. プロジェクト概要

ブラウザ上で動作する画像物体検知アプリケーションを開発する。

基本となる物体検知モデルは開発者側で作成・提供する。

ユーザーは、開発者が提供したモデルを利用して画像の物体検知を実行し、検知結果を確認できる。また、ユーザー自身が用意した学習データを利用して、既存モデルに対する転移学習をブラウザ上で実行できるようにする。

本システムでは、画像、アノテーション、データセット、モデル、学習結果、推論結果など、アプリケーションで扱うデータを基本的にすべて管理対象とする。

---

# 2. 基本要件

## 2.1 実行環境

システムは**ブラウザベース**とする。

現時点では、推論・データ管理・転移学習を含め、基本的にブラウザ内で実行することを前提とする。

したがって、システム構成を検討する際、サーバーを必須コンポーネントとして設計しない。

将来的にGPUサーバー等を利用した学習機能を追加する可能性はあるが、これは拡張事項とする。

---

# 3. ユーザーが行う操作

ユーザーの主要な操作は以下とする。

### 3.1 モデルを利用した物体検知

1. 使用するモデルを選択
2. 画像を入力
3. モデルを実行
4. 物体検知結果を表示
5. ユーザーが検知結果を確認

検知結果は表示するだけでなく、後から追跡できるように管理対象とする。

---

### 3.2 学習データの作成

ユーザーは画像を登録し、物体検知用のアノテーションを作成できる。

例えば、

```text
画像
 ↓
アノテーション
 ↓
データセット
```

という流れで管理する。

---

### 3.3 転移学習

ユーザーは、既存のモデルをベースとして転移学習を実行する。

基本的な流れは、

```text
既存モデル
   +
学習用データセット
   ↓
転移学習
   ↓
新しいモデル
```

とする。

ユーザーはモデルをゼロから作成するのではなく、開発者が提供したモデル、または既に存在するユーザーモデルをベースにして新しいモデルを作成できるものとする。

---

# 4. モデル管理方針

モデルについては、単純なモデル一覧として管理するのではなく、**モデルの派生関係（モデル系譜 / Model Lineage）を管理する**。

例えば、

```text
開発者モデル A
      │
      │ 転移学習
      ↓
ユーザーモデル B
      │
      │ 転移学習
      ↓
ユーザーモデル C
      │
      │ 転移学習
      ↓
ユーザーモデル D
```

という関係を追跡できるようにする。

特に、

> 「このモデルは、どのモデルから派生したのか」

を必ず追跡できる設計とする。

---

# 5. MODELとTRAININGを分離する

モデルそのものと、モデルを生成した学習処理は別の概念として扱う。

### MODEL

モデルそのものを表す。

例：

```text
MODEL
- model_id
- name
- model_type
- version
- parent_model_id
- model_data
- created_at
- ...
```

`parent_model_id`などによって、どのモデルから派生したかを追跡できるようにする。

ただし、派生関係をMODELの自己参照だけで表現するか、別のモデル系譜テーブルを設けるかは設計時に検討する。

---

### TRAINING

モデルを生成するために実行した学習処理を表す。

例：

```text
TRAINING
- training_id
- source_model_id
- output_model_id
- dataset_id
- training_parameters
- started_at
- completed_at
- training_result
- ...
```

これにより、

```text
Model A
   │
   │ source_model
   ↓
Training X
   │
   │ output_model
   ↓
Model B
```

という関係を管理できる。

さらに、

> Model Aを、Dataset Xを使い、どのような学習条件で学習した結果、Model Bが生成されたか

まで追跡可能にする。

---

# 8. 推論結果も管理する

推論結果は、一時的な画面表示だけの情報として扱わない。

例えば、

```text
Inference
├─ inference_id
├─ model_id
├─ image_id
├─ executed_at
└─ ...

Detection Result
├─ detection_id
├─ inference_id
├─ class
├─ confidence
├─ bounding_box
└─ ...
```

のように、推論を実行した事実と、その結果を管理できる構造を検討する。

これにより、

> 「どの画像に対して、どのモデルを使い、いつ推論を実行し、何を検出したか」

を追跡できるようにする。

# 10. データ保存

ブラウザ内で大量の画像・アノテーション・モデル等を扱うため、ブラウザストレージを利用する。

第一候補としてIndexedDB等を検討する。

概念的には、

```text
Browser Storage
│
├── Images
├── Annotations
├── Datasets
├── Models
├── Trainings
├── Training Results
├── Inferences
└── Detection Results
```

のような構成を想定する。

ただし、実際のDB構造・ストレージ方式は、データ容量やモデルサイズ等を考慮して設計時に決定する。

---

# 11. 重要な設計思想

今回のシステムでは、以下を重要な設計方針とする。

### ① モデルと学習処理を分離する

モデルそのものと、それを生成したTrainingを別の概念として管理する。

### ② モデルの系譜を追跡可能にする

すべてのユーザーモデルについて、

```text
このモデルは何をベースに作られたのか
```

を追跡できるようにする。

### ③ データを捨てない

画像、アノテーション、データセット、学習結果、推論結果など、アプリケーション上で意味を持つデータは原則として管理対象とする。

### ④ 推論結果を履歴として扱う

単なる画面表示ではなく、どのモデルによる結果なのかを追跡できるようにする。

### ⑤ ブラウザ完結を基本とする

現時点ではサーバーを前提とせず、ブラウザ上で推論・学習・データ管理を行う。

### ⑥ MLエンジンをアプリケーションから分離する

将来的なMLランタイム変更を容易にするため、アプリケーション層が特定のMLライブラリに直接依存しない構造を目指す。

# 12. 次の作業

次の設計作業では、まず**ER図を作成する**。

最初から物理DBのテーブル設計に入るのではなく、概念ER図として以下を整理する。

```text
Image
Annotation
Dataset

Model
Model Lineage

Training
Training Result

Inference
Detection Result
```

特に以下を明確にする。

* ModelとModelの派生関係
* ModelとTrainingの関係
* TrainingとDatasetの関係
* DatasetとImageの関係
* ImageとAnnotationの関係
* ModelとInferenceの関係
* InferenceとDetection Resultの関係
* Model Versionを独立エンティティにする必要があるか
* Model Lineageをどのように表現するか

ER図を確定した後、そのER図を基にシステム構成図、ブラウザ内コンポーネント構成、ストレージ設計へ進む。

現時点では、具体的なライブラリ・フレームワーク・DB実装を先に決定しない。

まずは**「何を管理し、何と何がどう関係するか」**を確定することを優先する。
